# AP-071 managed-channel isolation candidate

`compose.ap071-isolation.yaml` runs the installed task gateway and the
registered agent in distinct containers. The containers use one numeric UID
only so the current owner-only Unix release socket can be shared. Their mount,
process and network namespaces are separate: the agent receives its own key
and action directory plus a private Docker volume at `/channel`, while the
gateway alone receives `/gateway-state`, `/operator` and provider egress. The
agent has no active non-loopback network interface. Neither container receives
the Docker socket.

The [installed Linux boundary probe](../../../docs/program-log/2026-10-26-ap071-container-boundary.md)
pins both local images, the gateway binary, actual mounts and namespaces,
the agent-side denial checks, and a gateway-to-agent Unix socket exchange.
A subsequent [installed container Airtable run](../../../docs/program-log/2026-10-26-ap071-container-read-write.md)
completed one bounded agent read and one exact-confirmed write in that topology,
with task, receipt, provider-count and independent effect evidence. Its
operator-held PAT and synthetic human signer establish a local mechanism
result; the revised Jules Google and production deployments remain separate.

For a separate local OS-boundary result, the [source-free Airtable installed
run](../../../docs/program-log/2026-10-26-ap071-macos-installed-agent-isolation.md)
used macOS Seatbelt to restrict every agent process, probed denied credential
and gateway-state access from that agent, and completed one managed read and
write.

## Prepare the installed artifacts

Build the gateway image from one reviewed Linux gateway binary placed at
`artifacts/auths-gateway` beside `Dockerfile.ap071-gateway`. Pass its trusted
SHA-256 through `AP071_GATEWAY_SHA256`, then push and pin the resulting image
by registry manifest digest. Use the separately built, digest-pinned installed
AP-070 agent image from the same reviewed revision. The gateway image build
verifies the binary digest and its executable entry point, and contains no
source checkout.

```sh
docker build -f Dockerfile.ap071-gateway \
  --build-arg AP071_GATEWAY_SHA256="$AP071_GATEWAY_SHA256" \
  -t auths-ap071-gateway:candidate .
```

The operator creates three absolute directories on the Docker host, each
owned by `AP071_RUNTIME_UID:AP071_RUNTIME_GID` with mode `0700`. The release
channel uses a separately initialized Docker volume: Docker Desktop's macOS
bind mount can expose a socket path while refusing the socket `chmod` required
by the installed agent. An owner-private Docker volume supports that operation
and gateway-to-agent Unix IPC.

| Variable | Mounted only into | Contents |
| --- | --- | --- |
| `AP071_GATEWAY_STATE_DIR` | gateway | Task, connection, credential and attempt journals |
| `AP071_OPERATOR_PRIVATE_DIR` | gateway | Reviewed installation and Jules grant inputs |
| `AP071_AGENT_DIR` | agent | Agent key, signed actions and released content |
| `AP071_CHANNEL_VOLUME` | both | One-shot agent Unix socket in an external Docker volume; read-only mount in gateway |

Initialize an empty volume once, before starting Compose. The initialization
container sets the volume root's ownership and mode; neither running service
has root privileges. Use the same pinned Python base image as the installed
agent image.

```sh
docker volume create "$AP071_CHANNEL_VOLUME"
docker run --rm --user 0:0 \
  --mount "type=volume,src=$AP071_CHANNEL_VOLUME,dst=/channel" \
  python@sha256:a0f57064cbdcd6285fa45f51237ab0b35ea8ebaed06a1f5973e89e19dfb86704 \
  sh -c 'chown "$1:$2" /channel && chmod 0700 /channel' sh \
  "$AP071_RUNTIME_UID" "$AP071_RUNTIME_GID"
```

Any absolute file paths in the gateway's installed materializer pins must
resolve inside `/operator`; the private task state must resolve inside
`/gateway-state`. Place no credential or human key in `/agent` or `/channel`.
The container user must not be root. Keep the gateway and agent images
digest-pinned; a mutable tag is not an acceptance artifact.

## Prove the boundary from the installed agent

Start the two containers, then run the probe from the **agent image**:

```sh
docker compose -f compose.ap071-isolation.yaml up -d
docker compose -f compose.ap071-isolation.yaml exec -T agent \
  python -m employee_read_agent.isolation_probe
docker compose -f compose.ap071-isolation.yaml ps
```

The probe fails unless `/agent` and `/channel` are owner-private, the gateway
and operator mounts and Docker socket are inaccessible, no non-loopback
interface is active, and a direct outbound connection is denied. Linux may
list inactive tunnel devices even with `network_mode: none`. Record
`docker inspect` mount, network and PID-namespace data for both containers as
independent deployment evidence.
Then run `auths-google-read-agent serve-release` **inside the agent container**
with its mounted key, socket `/channel/agent.sock`, output under `/agent`, and
the signed task's exact ID, commitment, operation, resource and channel.
Execute the matching `auths-gateway task-read-submit` **inside the gateway
container** using the installed state and signed proof files. For the write
half, execute the agent's signing command in the agent container and the
gateway's task submit in the gateway container. Verify from the agent
container that credential files and operator CLI state cannot be opened and
that direct provider egress remains unavailable. Compare the gateway receipt
and independent provider count with the signed task; do not infer isolation
from the Compose file alone.

The two containers are long-running CLI hosts for this controlled test.
Their `sleep` entry points carry no authority. A later service deployment
may replace them with supervisors while preserving the same namespaces and
mounts.
