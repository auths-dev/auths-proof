## 1. Product decision and boundary

A useful delegation sounds like: **“Read these sources, draft an update, and put the approved update in this destination.”** The human sees the actual connected account, sources, destination, agent, expiry and limits. The agent has its own registered principal and key, runs in a separate process, and receives no human signing key or provider token. Google Workspace supplies the first installed example; another service must be expressible with the same Auths task, approval, read-release and write mechanisms by changing reviewed recipe data and its domain reference tests.

The product goal is a reusable answer to five questions for every agent action: **who** is acting, **on whose authority**, **with which connected account**, **on which resource**, and **within which limits**. A provider's own ACL and OAuth scope remain in force. Auths adds a narrower, revocable delegation and an evidence trail; it does not become a replacement for the provider's login or permission system. The user is not asked to author HTTP requests, JSON recipes, resource IDs or signing material.

The default write mode requires the human to confirm the **exact proposed change** after the agent has read and drafted it. A second, separately tested mode permits one tightly bounded write up front when company policy allows it. Both modes use the same native Auths authority checks and credential-isolated production write gateway. A read grant alone never authorizes a write. The human's provider authorization is a separate, subject-bound connection; Auths authority narrows that authorization and never expands it.

The first live acceptance effect is an edit to a disposable Google Doc inside a real Project A folder. For the smallest installed edit milestone, the agent reads demo_co's pinned Jules-owned Project A probe Doc, drafts a grounded update, and changes only the separate run-owned working Doc after Jules's exact confirmation. The full acceptance run also reads the existing canonical Project A status document as selected source context. Jules can open the result; demo_co independently compares the Doc identity, content and marker state in a private verifier and exports a keyed commitment and verdict. The canonical status Doc stays unchanged.

A second Google acceptance scenario creates a new Doc in that folder and fills it with the approved draft. This tests creation and editing as two distinct provider effects. An initial Jules task exercised response-derived child binding but its paired population was refused; a separate populate-only task later filled that child. A later local run used one human-signed plan for a new child and its population, with independent demo_co inspection. This is a live milestone; full AP-SPEC-071 completion still requires the rest of §9.

### 1.1 Human and agent journey

1. An operator installs reviewed read and write recipes for a service and defines which connection types and company policies may use them. This is setup, not an approval the employee repeats for every task.
2. The human signs in, connects an existing provider account, and chooses named sources and destinations through a provider-aware picker. The UI resolves names to pinned resource handles and shows the connected account and any observed access checks; it never implies that Auths can grant access the provider denies.
3. The human describes the job and reviews a concise task card: agent identity, purpose, readable resource names, allowed read/write verbs, content destination, expiry, call/byte/effect limits, and whether writes require exact confirmation. The signed grant commits to the structured card, not merely to its prose. If the agent later needs a new source, destination or verb, it requests a new human approval.
4. The separately identified agent requests bounded source content under that grant. Auths releases only the selected content to the designated agent and records what was released without exposing the human's provider credential. The agent drafts an action and cites the source it used.
5. By default the human sees the exact proposed change and destination before it can enter the provider. A separately selected, policy-permitted mode may allow a finite set of writes up front. The agent signs the actual action in either mode.
6. The human sees an activity timeline showing approvals, releases, provider entry, observed effects and unknown outcomes. They can revoke future use. Revocation does not undo an entered write or remove content already delivered to an agent.

The same journey and terms MUST work when the Google recipes are replaced by another provider's reviewed recipes. Provider-specific pickers and effect previews can show familiar names and links, but they cannot change the shared approval or authority semantics. A demo that requires an operator to hand-edit the task's raw JSON, or lets the agent choose a new provider URL at runtime, does not meet the product goal.

## 2. Common task and permission model

Real agent work often combines reading context with one of these effects: drafting a new artifact, updating an existing artifact, changing structured status, sending a message, or sharing an artifact. The Google demo chooses **edit and create** because a human can inspect the actual artifact and its history. Sending, sharing, deleting, moving and changing ACLs are separate capabilities with different approval and recovery rules; none is implied by a generic “write” permission.

An Auths task is a human-reviewed envelope: company and human identity; agent principal and key fingerprint; provider accounts and connection generations; exact source and destination resource handles; allowed verbs; content destination; expiry; call, byte and write budgets; approval mode; and operator policy version. Its core representation does not contain Google file IDs, Google OAuth scopes, HTTP URLs, JSON pointers or provider-specific request semantics. Those live in connection records, reviewed recipe data and domain reference tests. Effective authority is the intersection of current provider access, operator-approved installation and policy, active Auths grant, exact action and any required exact-write confirmation. Provider denial remains a denial. The UI distinguishes **task approved**, **read delivery entered**, **agent acknowledged read**, **read delivery unknown**, **write proposed**, **write confirmed**, **provider write entered**, **effect observed** and **outcome unknown**.

A later composite task may present one 30-minute approval covering several connected accounts, such as calendar, email and SQL, while deriving a separate scoped child grant, budget and receipt for each service and operation. The task expiry caps every child; revocation stops future admissions across the bundle. “Same permissions as me” can be a convenient scope proposal only for connected resources whose available actions can be enumerated, reviewed and enforced by installed recipes and company policy. It does not mint a provider credential, make inaccessible systems accessible, or turn one service's authorization into another's. Sending mail, changing database rows, sharing and deleting remain explicit effect classes, with exact confirmation by default for consequential changes. Cross-provider composite admission and its UI are future work; the current installed gateway binds one write connection per task session.

The person authenticates through the company's identity provider; the provider connection binds the person's stable subject, account, scopes and credential generation. Browser login, provider API consent and Auths task approval are distinct events. For Google specifically, Jules already has a checked Desktop OAuth `drive.file` grant that demo_co reports can read the Project A probe Doc and edit the working Doc. Auths must independently bind and lease that same Jules subject before claiming a live read or write. Any wider Google scope would require explicit operator and Jules review in the synthetic tenant. Record the actual scope. An admin grant may provision and inspect fixtures, but MUST NOT execute the agent's write.

The same task may contain separate narrow native read and write grants if the current profile cannot encode both. Each agent action is signed over its canonical body, task ID and signed task-card commitment, resource handle, recipe digest, challenge, limits and operation ID. No agent-supplied URL, provider credential selector, arbitrary resource ID, body shape or OAuth scope is accepted.

**Connection topology for a mixed task:** the signed task card binds a connection ID, generation, provider account subject and recipe digest to each read and write scope. A read scope must match an operator-permitted scope; the installed write session also binds each write scope to its single installed write connection. The release ledger binds a claimed read to the selected subject and generation. A read recipe uses the same canonical descriptor contract as a write recipe, and its credential-bearing transport sends a bounded GET, including a recipe-fixed query. The development operator can now install a distinct read connection, recipe, private credential journal and rollback floor, then bind it to the activated task and authenticated agent channel through `task-read-configure` and `task-read-submit`. The live Jules read and agent acknowledgment passed on 25 October 2026; post-claim OAuth renewal and production custody/qualification remain before full acceptance. An action selects a unique signed scope by task ID, resource handle, verb and recipe digest; it cannot supply a new connection. Multiple references may resolve to Jules's same Google subject and OAuth client, but the UI shows their account and access separately and no credential crosses to the agent. A changed generation or account subject requires a new task approval. demo_co confirmed the one checked Jules `drive.file` grant can back both bounded Project A read and write connections without a new fixture or consent, provided Auths pins the same Google subject and Desktop OAuth client. That bearer is write-capable, so the read connection is read-only because its reviewed gateway recipe and transport enforce GET and release limits. A future shared credential vault may avoid copying short-lived bearer material between installations; the demo may install two independently bound gateway connections from the one broker-held grant.

The gateway can validate a closed connection descriptor containing two to four task-bound write recipes under one credential. Task activation checks every signed write scope against a sorted, operator-installed digest set and requires that set to equal the connection descriptor's set. A development installation can now hold the Google edit and create recipes under one connection record and task journal; `task-submit` selects a digest from that installed set, while the agent's native action remains bound to the selected recipe. A human-signed task card may also name one pending child proposal: it fixes the create operation, parent, title, marker, and create/populate recipe digests. Activation requires both digests in the installed set, and create admission checks the signed fields. This proposal is not a usable populate scope. A ledger test reserves a create and an edit under two recipe digests, restarts the store, and proves their combined budget and replay refusal. A matched credential-bearing metadata observation now stores one immutable child binding in that task journal, tied to the reserved create, response and metadata digests, and subject/generation. The task journal now derives one one-time populate scope from that binding; a fresh agent action and exact human confirmation must match its child ID and recipe digest, and a second population operation is refused. The dedicated recorded-response crash reconciliation now has a synthetic restart test. A new native effect-plan action can bind the exact create intent, one populate recipe and operation, initial text and expiry in the private task journal before a write; altered signatures, changed content and restart replay are tested. The exact create can now consume that recorded plan without a second confirmation, and a loopback test enters one provider create, loses the metadata response, then binds the child after restart using only the original agent proof and stored plan. A signed, operator-pinned preflight report can now bind the response-derived child, Jules subject/generation, tab and revision to that plan in the private journal. Planned population compares the complete agent request with those facts and the approved text, then spends the shared second-write budget. A synthetic loopback test enters one create and one population with one human plan, including crash reconciliation, altered-text refusal and replay refusal. Live Google execution, installed signer/key custody, lost-response recovery binding and independent producer observation remain.

For the first live journey, the human selects one existing source Doc and one run-owned working Doc or destination folder by name. The UI commits their resolved provider IDs while displaying the names and account. A task may include a finite set of selected resources. Broader phrases such as “anything in Project A” require an operator-reviewed discovery recipe and a provider-checked membership rule before the agent can enumerate or read children; a folder label alone is not a wildcard grant. A newly created child becomes usable for a follow-up action only through the task-bound response binding described in §3.2. This keeps the human experience simple without turning natural-language scope into executable authority.

| Layer | Owns | Example values that stay out of shared logic |
| --- | --- | --- |
| Auths task and native authority | Human and agent identity, signed resource handles, verbs, approval mode, expiry, budgets, exact confirmation and receipts | No provider endpoint or field mapping |

Adding a service still requires a provider connection, reviewed recipes, resource presentation and domain tests. It MUST NOT require a new human-to-agent delegation protocol, a new Auths receipt meaning, provider-specific branches in the shared gateway, or a second production executor. The expected integration unit is an operator-installable recipe plus its reviewed domain reference. If a service needs a transport or custody behavior outside the closed recipe grammar, that behavior is a separately reviewed capability with evidence from independent domains before promotion. If it needs different provider semantics, those stay in its vertical.

## 3. Recipe-based execution contract

### 3.1 Read release is a new closed capability

The gateway's existing GETs are credential checks, pre-entry conditions or post-write observations. They MUST NOT be treated as an agent-facing content-release API: they do not specify what private bytes may be shown to which agent or destination. AP-SPEC-070's Google broker remains a bounded application-owned first vertical until a separately reviewed managed read-release mechanism exists. Its successful Google read is evidence for that vertical, not proof of a general read gateway.

A managed read-release recipe is immutable, versioned, operator-reviewed data bound by digest in the native action. It fixes an HTTPS origin and method, path template with typed resource fields, permitted query/header shape, connection generation and subject, response status and media type, maximum response and released byte counts, bounded projection or extraction, release destination, expiry and per-task budgets. The agent supplies only signed, verified field values and never a raw URL, HTTP body, selector or credential. The credential-owning process spends one provider-call allowance before a provider request, sends the request, checks its account binding and response, and releases only the approved projection to the named agent channel. A failed or partial provider response or projection releases nothing and spends no released-byte allowance, although its provider call remains counted. Released content is untrusted input to the agent and cannot alter task authority. Revocation prevents a later release; it cannot recall bytes already delivered.

**Release accounting and commit point.** Before the first byte enters the agent channel, the custody service atomically claims the logical read operation, durably records `release-entered`, and irreversibly charges the projected byte count and one release against the task budgets. It then sends those exact bytes to the named agent. A complete, authenticated agent acknowledgement bound to the operation ID and the delivered bytes advances the receipt to `agent-acknowledged`; it records the agent's acknowledgement of that delivery, not independent proof that the agent understood or used the content. If a send may have begun but the acknowledgement is missing, including when the acknowledgement itself is lost, the receipt is `delivery-unknown`: the budgets remain spent, and the UI cannot call it a completed release. A proven failure before `release-entered` is `not-entered` with zero agent-visible bytes. A failure after the durable claim but with proof that the private content-byte send did not begin is conservatively charged and recorded as `not-delivered`; length framing may have been observed, and the charge is not refunded. A crash without that proof stays `delivery-unknown`. The same operation ID is never delivered again automatically. A deliberate new read needs a new signed action, task admission and remaining budget, even when the content appears unchanged. Crash/restart tests must cover every transition and prevent a second send of a claimed operation.

The native acknowledgement verifier now checks an Ed25519 signature under the exact registered agent identity descriptor pinned in the human-signed task card. It uses the general descriptor and `default-signing` preimage emitted by the existing Python agent registry, then validates that descriptor's one raw-key relationship against the card's target-V1 agent principal. Its signed message binds the task commitment, operation, resource, channel, byte count and exact content digest. That plain digest exists only in the private channel exchange; public receipts retain the keyed commitment. An internal Unix-socket channel challenges that registered key with a fresh operation-bound nonce before sending content, then sends bounded exact bytes and verifies the acknowledgement. A one-shot command in the separate Python agent package now receives the bounded bytes into a private file and signs the exact receipt message only after saving them. Its local subprocess test verifies the handshake and a changed-content refusal. The agent command reports `acknowledgement-sent`; only the gateway's durable ledger can claim `agent-acknowledged`. A signature is the agent key's acknowledgement, not proof of comprehension or use. The current socket prototype requires a private directory and socket owned by the gateway UID; that is a development process boundary, not the full separate-UID agent isolation required by §7. The installed Jules and Airtable provider-to-agent runs have exercised it.

Receipts, public exports and logs MUST NOT expose raw private content or an unkeyed hash of it. They carry a keyed content commitment (for example HMAC-SHA-256 under an audit key kept in custody), domain-separated by task, resource, operation and receipt kind, plus the key version, byte count, recipient and transport state. This applies even to short fields such as Airtable `DemoStatus`, whose possible values are easy to guess. A private verifier may compare provider bytes with released bytes in memory and publish only a verdict; demo_co may keep its own independent evidence commitment. Key rotation must preserve verification of retained receipts without publishing the key or turning the commitment into a cross-task content identifier.

This is a proposed product boundary with a development gateway implementation; production qualification and the independent evidence gates remain open. [Abstraction case 0009](../research/domains/abstraction-cases/0009-agent-content-release.md) compares the Google and Airtable domains; [ADR 0017](../adr/0017-closed-agent-content-release.md) proposes the shared mechanism and remains unaccepted until its independent evidence gates pass. Keep provider meaning, permission interpretation, citation rules and content-safety checks in vertical references and reviewed recipe policy. The interpreter MUST NOT branch on provider or operation names, load provider code, accept runtime URLs, or become a general credential proxy. Its capability AST, compiler, review output, hostile fixtures, custody boundary, release accounting, restart behavior and installed evidence each need a release gate.

Checked-in [Google Drive text](../../demos/google-employee-delegation/read_reference/README.md) and [Airtable field](../../demos/airtable-gateway/read_reference/README.md) references compile with the same release grammar and distinct response projections. The development gateway now joins that grammar to task admission, a separate credential journal, budgets and an authenticated local delivery channel. The Google and Airtable references have live provider-to-agent release evidence under the development installation; production qualification remains open.

An internal single-host task journal tests provider-call reservation, an atomic release/byte charge before delivery, replay refusal, revocation, restart and competing claims. It records a terminal `release-refused` stage when an already reserved call cannot proceed because credential, connection, policy or release budget has changed; no content is sent and the provider-call allowance stays spent. The authenticated channel can construct `agent-acknowledged` evidence only after its exact-byte send. It now supplies `not-delivered` evidence if length framing fails before the first private content-byte write; the gateway durably records that stage and keeps the release/byte charge. Channel, ledger restart and joined gateway tests pass with a controlled pre-content fault. An installed end-to-end no-send fault run remains open. A provider-neutral task-card model verifies a human-signed native action under operator-pinned company, agent, connection, delivery and policy facts. Only that approved card may initialize the read journal. A native verifier projects one signed agent action and exact human-issued terminal grant into a private closed release request; the journal binds its actor, human issuer, task-card commitment, listed source, recipe digest and connection generation before charging. An internal engine path joins that task, connection, credential lease, bounded provider GET, projection, ledger and channel, rechecking the connection and expiry before release entry. A synthetic joined test uses a subject-bound connection, real native proof, an in-process loopback provider and a separately keyed Unix socket peer; it verifies one provider call, the five projected bytes, the agent acknowledgement and persisted accounting. The development read operator command and installed Jules and Airtable runs now exist; multi-host storage, full agent isolation and the remaining installed negative cases remain open.

The read recipe needs its own qualification gate. A qualification for the installed write recipe cannot qualify a different read digest, even when both records lease the same Jules grant. The internal executor now accepts a separately installed read gate and checks it before leasing and before release. A read session joins the activated task journal, but requires an operator-pinned read recipe and registered recipient; construction refuses an unlisted recipe or changed agent identity packet. The synthetic joined test first shows that an unqualified read or altered agent action consumes no provider-call allowance, then runs one admitted read through that session under an optional development read gate. The development operator CLI can install a distinct read connection, private credential journal, recipe and agent channel; a synthetic CLI test checks the separate journal and rollback floor. This does not qualify the recipe or prove a live provider release. Task activation currently rides on the write installation; a unified task installation is needed so a read-only task does not depend on a dummy write recipe.

The operator can now run `auths-gateway review-release` offline to obtain the compiler's exact read recipe digest and bounded GET policy before issuing a mixed task package. The package pins the reviewed read source/profile bytes, service, tool and parent grant; the card chooses an exact operator-pinned source and budgets one release. This offline review does not install a read connection or qualify the recipe.

### 3.2 Writes use the existing general gateway

Every production provider write uses ADR 0012's data-only, credential-isolated gateway. A write recipe fixes the target origin, typed path, bounded fixed query, request shape, credential binding, limits and any observation rule. The fixed query is operator-reviewed and compiled into the recipe digest; the transport checks its exact encoded value, and the agent cannot supply query fields. This shared mechanism permits a future Google Drive create recipe to declare `supportsAllDrives=true` without a provider branch. The native agent action and, for exact mode, human confirmation bind the operation ID, resource, recipe digest and exact intended effect. Provider-specific effects, idempotency and retry safety stay in vertical reference tests and operator review. The gateway reports verified, admitted, entered, response-recorded and, where available, observed stages without inventing provider success. An ambiguous entered write is outcome_unknown and is not blindly retried.

The construction contract now derives a private exact-write intent from a native-verified agent action, the signed task card, a reviewed recipe resource field and the compiled closed request. It binds the task-card commitment, action commitment, closed request commitment, operation ID, resource handle, recipe digest, connection subject/generation and verb. A second native human action must sign that same intent for exact mode; the separately enabled bounded-upfront mode cannot borrow an exact confirmation. The Google Docs and Airtable v2 write references carry task ID and card commitment fields and declare the same provider-neutral `task_binding` over their respective document and record fields. The Airtable reference proves only closed request construction under the same compiler; it uses an operator PAT and does not prove human delegation. Ordinary installed `submit` now refuses any such recipe before a claim or lease. A task-aware engine path verifies the human-signed card once at activation, stores its full card and commitment in the private journal, then checks that activation by task ID, current operator pins, expiry and revocation while verifying each fresh agent action and exact confirmation (or the separately enabled upfront mode). It derives the same intent during submission, durably reserves a write in the common task journal before the provider attempt claim, and checks the loaded connection ID, generation and provider-account-subject commitment before credential lease. Installations serving task writes therefore set the connection's account label to the provider's stable subject. It conservatively spends that write slot if a later preparation, claim or transport step fails. Development installations now expose an operator-owned CLI path with canonical private pins, one-time task activation and task submission; production remains refused because the task journal is single-host. A broker-side development shim validates the pinned demo_co generation and Jules’s separate `drive.file` grant, checks her current UserInfo subject, and pipes a short-lived bearer into a new gateway installation with that subject as the account label. It was synthetic-tested and then installed Jules's subject-checked short-lived credential for the live edit and create milestones; post-claim renewal remains incomplete. A synthetic installed test now signs a task card, agent action and exact human confirmation, executes the Airtable-shaped write and readback through a local provider double, observes the effect and refuses replay without a second lease. This proves the common gateway path under test keys and an operator PAT, not human-provider delegation in Airtable. The human task and exact-confirmation UI now support the live Jules edit milestone: a distinct agent read, drafted and signed, Jules confirmed, the gateway submitted one edit, and demo_co independently observed it. The owner-side CLI and credential shim are development integration; they do not prove production credential custody or cross-provider human delegation. Request/action commitments can reveal low-entropy private content if published; they stay inside confirmation custody and are not public receipts.

The gateway's installed native trust must authorize the provider action profile and the two fixed `auths-agent-task` approval profiles. Its default request audience remains the provider service for agent actions. During task activation and exact confirmation, the gateway rebinds only the verifier's expected audience to the code-defined `mcp://auths-agent-task` audience; an agent submission cannot choose that value. The operator-owned task session refuses a trust context whose anchors lack either task profile permission, namespace or audience. Activation also checks that the subject-bound connection currently approves the installed recipe. Synthetic tests verify all three action types under the same trust configuration. ### 3.3 One task, separate authorities and receipts

Read and write grants are distinct; their counters and receipts remain distinct. The common task ledger correlates them by signed task ID and source/destination handles. A read receipt states whether delivery was entered, acknowledged or remains unknown; only an authenticated acknowledgement supports an agent-acknowledged claim. A write receipt proves the gateway's stage and any independently observed effect. ## 7. Exact confirmation and operating rules

The write proposal screen shows the source citation and content destination; before and after text; connected human account, destination label/link and opaque resource handle; applicable version/precondition; agent identity; recipe; maximum effect count; expiry; and whether this is edit or create. The human's confirmation signs a canonical digest covering those fields and the exact content bytes or their canonical digest. The agent's later action must match byte-for-byte. For Google, the screen also resolves the Doc/folder IDs and current revision through its reviewed vertical. Google login alone is not a write confirmation.

Revocation blocks new admission and leases after its documented commit point. The development operator can call `task-revoke` on the shared task journal; synthetic read and write tests prove subsequent actions stop before a provider lease. The Jules task screen offers a revoke control that checks the signed task's employee owner and calls that operator command. It renders a short activity timeline from the redacted durable task status: budgets, read delivery stages, claimed write operation IDs and revocation. A claimed write is labeled as such, never as an observed effect; joining gateway attempt and independent provider evidence into this timeline remains to be built. Revocation cannot retract released read content or undo an entered write. Read release and write effect have distinct receipts and limits. Agent and gateway have separate filesystem and network boundaries; the agent cannot inspect the OAuth vault, human signing key, operator interface or admin fixture grant. A prompt inside the source document is untrusted data and cannot change the approved destination. Logs, export and evidence contain no tokens or private document text.
