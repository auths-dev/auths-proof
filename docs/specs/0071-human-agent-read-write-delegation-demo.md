# AP-SPEC-071: Human-to-agent task delegation across providers

- **Status:** Implementation in progress. Provider-neutral task admission, a synthetic installed write path, and an internal managed read executor with an authenticated local agent channel exist. The read executor is not exposed through an installed operator command or proven in a full provider-to-agent run; the live Google edit/create journeys and cross-provider acceptance remain incomplete.
- **Date:** 25 October 2026.
- **Scope:** A human delegates a short task with separately bounded read and write authority to an identified agent. Auths gives the person one understandable approval and activity experience across connected services. Reusable task, approval and receipt mechanics are provider-neutral; operator-reviewed recipes describe provider requests. The installed Atlas/Google scenario is the first live acceptance case.
- **Depends on:** [AP-SPEC-070](0070-google-employee-agent-delegation-demo.md), [AP-SPEC-051](0051-self-hosted-developer-profiles.md), [AP-SPEC-063](0063-generalized-gateway.md), [ADR 0012](../adr/0012-declarative-credential-isolated-gateway-boundary.md), [ADR 0013](../adr/0013-recipe-capabilities-and-sum-budget.md), and the [domain boundary plan](../target-state/PROFILE_AND_DOMAIN_ABSTRACTION_BOUNDARY_PLAN.md).
- **Producer:** demo_co owns the company accounts, Project A Google fixtures, provider ACLs, independent probes, versioned export and cleanup. Auths owns human-to-agent authority, admission, credential-isolated execution, receipts and the task UI.
- **Normative terms:** MUST and MUST NOT are requirements. Proposed contract names are illustrative until registered.

## 1. Product decision and boundary

A useful delegation sounds like: **“Read these sources, draft an update, and put the approved update in this destination.”** The human sees the actual connected account, sources, destination, agent, expiry and limits. The agent has its own registered principal and key, runs in a separate process, and receives no human signing key or provider token. Google Workspace supplies the first installed example; another service must be expressible with the same Auths task, approval, read-release and write mechanisms by changing reviewed recipe data and its domain reference tests.

The product goal is a reusable answer to five questions for every agent action: **who** is acting, **on whose authority**, **with which connected account**, **on which resource**, and **within which limits**. A provider's own ACL and OAuth scope remain in force. Auths adds a narrower, revocable delegation and an evidence trail; it does not become a replacement for the provider's login or permission system. The user is not asked to author HTTP requests, JSON recipes, resource IDs or signing material.

The default write mode requires the human to confirm the **exact proposed change** after the agent has read and drafted it. A second, separately tested mode permits one tightly bounded write up front when company policy allows it. Both modes use the same native Auths authority checks and credential-isolated production write gateway. A read grant alone never authorizes a write. The human's provider authorization is a separate, subject-bound connection; Auths authority narrows that authorization and never expands it.

The first live acceptance effect is an edit to a disposable Google Doc inside a real Project A folder. The agent reads the existing canonical Project A status document and current working Doc, drafts a grounded update, and changes only the run-owned working Doc after Jules's exact confirmation. Jules can open the result; demo_co independently compares the Doc identity, content and marker state in a private verifier and exports a keyed commitment and verdict. The canonical status Doc stays unchanged.

A second Google acceptance scenario creates a new Doc in that folder and fills it with the approved draft. This tests creation and editing as two distinct provider effects. It is a later implementation slice because the current gateway has no reviewed task-bound chaining of a newly returned resource ID into a second write. The initial live edit may be reported as an **edit milestone**; AP-SPEC-071 completion requires both scenarios and the cross-provider conformance in §6.

### 1.1 Human and agent journey

1. An operator installs reviewed read and write recipes for a service and defines which connection types and company policies may use them. This is setup, not an approval the employee repeats for every task.
2. The human signs in, connects an existing provider account, and chooses named sources and destinations through a provider-aware picker. The UI resolves names to pinned resource handles and shows the connected account and any observed access checks; it never implies that Auths can grant access the provider denies.
3. The human describes the job and reviews a concise task card: agent identity, purpose, readable resource names, allowed read/write verbs, content destination, expiry, call/byte/effect limits, and whether writes require exact confirmation. The signed grant commits to the structured card, not merely to its prose. If the agent later needs a new source, destination or verb, it requests a new human approval.
4. The separately identified agent requests bounded source content under that grant. Auths releases only the selected content to the designated agent and records what was released without exposing the human's provider credential. The agent drafts an action and cites the source it used.
5. By default the human sees the exact proposed change and destination before it can enter the provider. A separately selected, policy-permitted mode may allow a finite set of writes up front. The agent signs the actual action in either mode.
6. The human sees an activity timeline showing approvals, releases, provider entry, observed effects and unknown outcomes. They can revoke future use. Revocation does not undo an entered write or remove content already delivered to an agent.

The same journey and terms MUST work when the Google recipes are replaced by another provider's reviewed recipes. Provider-specific pickers and effect previews can show familiar names and links, but they cannot change the shared approval or authority semantics. A demo that requires an operator to hand-edit the task's raw JSON, or lets the agent choose a new provider URL at runtime, does not meet the product goal.

## 2. Common task and permission model

Real agent work often combines reading context with one of these effects: drafting a new artifact, updating an existing artifact, changing structured status, sending a message, or sharing an artifact. The Google demo chooses **edit and create** because a human can inspect the actual artifact and its history. Sending, sharing, deleting, moving and changing ACLs are separate capabilities with different approval and recovery rules; none is implied by a generic “write” permission.

An Auths task is a human-reviewed envelope: company and human identity; agent principal and key fingerprint; provider accounts and connection generations; exact source and destination resource handles; allowed verbs; content destination; expiry; call, byte and write budgets; approval mode; and operator policy version. Its core representation does not contain Google file IDs, Google OAuth scopes, HTTP URLs, JSON pointers or provider-specific request semantics. Those live in connection records, reviewed recipe data and domain reference tests. Effective authority is the intersection of current provider access, operator-approved installation and policy, active Auths grant, exact action and any required exact-write confirmation. Provider denial remains a denial. The UI distinguishes **task approved**, **read delivery entered**, **agent acknowledged read**, **read delivery unknown**, **write proposed**, **write confirmed**, **provider write entered**, **effect observed** and **outcome unknown**.

The person authenticates through the company's identity provider; the provider connection binds the person's stable subject, account, scopes and credential generation. Browser login, provider API consent and Auths task approval are distinct events. For Google specifically, the existing Jules drive.readonly grant is not silently upgraded. A new write-capable Jules consent and subject/connection binding are required. Prefer drive.file if the live folder/file access probe proves it works; if it cannot address the producer-owned folder and working Doc, a dedicated drive-scope consent may be used only after explicit operator and Jules review in the synthetic tenant. Record the actual scope. An admin grant may provision and inspect fixtures, but MUST NOT execute the agent's write.

The same task may contain separate narrow native read and write grants if the current profile cannot encode both. Each agent action is signed over its canonical body, task ID and signed task-card commitment, resource handle, recipe digest, challenge, limits and operation ID. No agent-supplied URL, provider credential selector, arbitrary resource ID, body shape or OAuth scope is accepted.

**Connection topology for a mixed task:** the signed task card now binds a connection ID, generation, provider account subject and recipe digest to each read and write scope. A read scope must match an operator-permitted scope; the current installed write session also binds each write scope to its single installed write connection. The release ledger binds a claimed read to the selected subject and generation. A read recipe can now use the same canonical descriptor contract as a write recipe, and a credential-bearing transport can send its bounded GET, including a recipe-fixed query. These are contract and transport steps, not an installed mixed-task journey: the read credential record, read recipe installation, custody admission and delivery session still need to check that operator-permitted reference at every entry. An action selects a unique signed scope by task ID, resource handle, verb and recipe digest; it cannot supply a new connection. Multiple references may resolve to Jules's same Google subject and OAuth client, but the UI shows their account and access separately and no credential crosses to the agent. A changed generation or account subject requires a new task approval. demo_co confirmed the one checked Jules `drive.file` grant can back both bounded Project A read and write connections without a new fixture or consent, provided Auths pins the same Google subject and Desktop OAuth client. That bearer is write-capable, so the read connection is read-only only because its reviewed gateway recipe and transport enforce GET and release limits. A future shared credential vault may avoid copying short-lived bearer material between installations; the demo may install two independently bound gateway connections from the one broker-held grant.

For the first live journey, the human selects one existing source Doc and one run-owned working Doc or destination folder by name. The UI commits their resolved provider IDs while displaying the names and account. A task may include a finite set of selected resources. Broader phrases such as “anything in Project A” require an operator-reviewed discovery recipe and a provider-checked membership rule before the agent can enumerate or read children; a folder label alone is not a wildcard grant. A newly created child becomes usable for a follow-up action only through the task-bound response binding described in §3.2. This keeps the human experience simple without turning natural-language scope into executable authority.

| Layer | Owns | Example values that stay out of shared logic |
| --- | --- | --- |
| Auths task and native authority | Human and agent identity, signed resource handles, verbs, approval mode, expiry, budgets, exact confirmation and receipts | No provider endpoint or field mapping |
| Operator-reviewed recipe and connection | Closed request/response grammar, typed fields, origin, credential generation, extraction, limits and digest | Google Docs path and body; Airtable table path and field |
| Test-only domain reference | Provider permission/effect meaning, safe retry, before/after probes and independent evidence | Docs revision and replacement count; Airtable record value |
| demo_co producer | Human accounts, ACLs, run-owned Google fixtures, independent probes and versioned exports | Project A folder, Jules subject, working Doc |

Adding a service still requires a provider connection, reviewed recipes, resource presentation and domain tests. It MUST NOT require a new human-to-agent delegation protocol, a new Auths receipt meaning, provider-specific branches in the shared gateway, or a second production executor. The expected integration unit is an operator-installable recipe plus its reviewed domain reference. If a service needs a transport or custody behavior outside the closed recipe grammar, that behavior is a separately reviewed capability with evidence from independent domains before promotion. If it needs different provider semantics, those stay in its vertical.

## 3. Recipe-based execution contract

### 3.1 Read release is a new closed capability

The gateway's existing GETs are credential checks, pre-entry conditions or post-write observations. They MUST NOT be treated as an agent-facing content-release API: they do not specify what private bytes may be shown to which agent or destination. AP-SPEC-070's Google broker remains a bounded application-owned first vertical until a separately reviewed managed read-release mechanism exists. Its successful Google read is evidence for that vertical, not proof of a general read gateway.

A managed read-release recipe is immutable, versioned, operator-reviewed data bound by digest in the native action. It fixes an HTTPS origin and method, path template with typed resource fields, permitted query/header shape, connection generation and subject, response status and media type, maximum response and released byte counts, bounded projection or extraction, release destination, expiry and per-task budgets. The agent supplies only signed, verified field values and never a raw URL, HTTP body, selector or credential. The credential-owning process spends one provider-call allowance before a provider request, sends the request, checks its account binding and response, and releases only the approved projection to the named agent channel. A failed or partial provider response or projection releases nothing and spends no released-byte allowance, although its provider call remains counted. Released content is untrusted input to the agent and cannot alter task authority. Revocation prevents a later release; it cannot recall bytes already delivered.

**Release accounting and commit point.** Before the first byte enters the agent channel, the custody service atomically claims the logical read operation, durably records `release-entered`, and irreversibly charges the projected byte count and one release against the task budgets. It then sends those exact bytes to the named agent. A complete, authenticated agent acknowledgement bound to the operation ID and the delivered bytes advances the receipt to `agent-acknowledged`; it records the agent's acknowledgement of that delivery, not independent proof that the agent understood or used the content. If a send may have begun but the acknowledgement is missing, including when the acknowledgement itself is lost, the receipt is `delivery-unknown`: the budgets remain spent, and the UI cannot call it a completed release. A proven failure before `release-entered` is `not-entered` with zero agent-visible bytes. A failure after the durable claim but with durable proof that transport did not begin is conservatively charged and recorded as `not-delivered`; it is not silently refunded. A crash without that proof stays `delivery-unknown`. The same operation ID is never delivered again automatically. A deliberate new read needs a new signed action, task admission and remaining budget, even when the content appears unchanged. Crash/restart tests must cover every transition and prevent a second send of a claimed operation.

The native acknowledgement verifier now checks an Ed25519 signature under the exact registered agent identity descriptor pinned in the human-signed task card. It uses the general descriptor and `default-signing` preimage emitted by the existing Python agent registry, then validates that descriptor's one raw-key relationship against the card's target-V1 agent principal. Its signed message binds the task commitment, operation, resource, channel, byte count and exact content digest. That plain digest exists only in the private channel exchange; public receipts retain the keyed commitment. An internal Unix-socket channel challenges that registered key with a fresh operation-bound nonce before sending content, then sends bounded exact bytes and verifies the acknowledgement. A one-shot command in the separate Python agent package now receives the bounded bytes into a private file and signs the exact receipt message only after saving them. Its local subprocess test verifies the handshake and a changed-content refusal. The agent command reports `acknowledgement-sent`; only the gateway's durable ledger can claim `agent-acknowledged`. A signature is the agent key's acknowledgement, not proof of comprehension or use. The current socket prototype requires a private directory and socket owned by the gateway UID; that is a development process boundary, not the full separate-UID agent isolation required by §7. No installed provider-to-agent run has yet exercised it.

Receipts, public exports and logs MUST NOT expose raw private content or an unkeyed hash of it. They carry a keyed content commitment (for example HMAC-SHA-256 under an audit key kept in custody), domain-separated by task, resource, operation and receipt kind, plus the key version, byte count, recipient and transport state. This applies even to short fields such as Airtable `DemoStatus`, whose possible values are easy to guess. A private verifier may compare provider bytes with released bytes in memory and publish only a verdict; demo_co may keep its own independent evidence commitment. Key rotation must preserve verification of retained receipts without publishing the key or turning the commitment into a cross-task content identifier.

This is a proposed product capability, not an assertion that the current gateway implements it. [Abstraction case 0009](../research/domains/abstraction-cases/0009-agent-content-release.md) compares the Google and Airtable domains; [ADR 0017](../adr/0017-closed-agent-content-release.md) proposes the shared mechanism and remains unaccepted until its independent evidence gates pass. Keep provider meaning, permission interpretation, citation rules and content-safety checks in vertical references and reviewed recipe policy. The interpreter MUST NOT branch on provider or operation names, load provider code, accept runtime URLs, or become a general credential proxy. Its capability AST, compiler, review output, hostile fixtures, custody boundary, release accounting, restart behavior and installed evidence each need a release gate.

Checked-in [Google Drive text](../../demos/google-employee-delegation/read_reference/README.md) and [Airtable field](../../demos/airtable-gateway/read_reference/README.md) references now compile with the same release grammar and distinct response projections. This establishes request construction and bounded extraction only; neither reference has the managed custody, task-admission, budget, delivery or installed-provider evidence required above.

An internal single-host task journal tests provider-call reservation, an atomic release/byte charge before delivery, replay refusal, revocation, restart and competing claims. It records a terminal `release-refused` stage when an already reserved call cannot proceed because credential, connection, policy or release budget has changed; no content is sent and the provider-call allowance stays spent. The authenticated channel can construct `agent-acknowledged` evidence only after its exact-byte send; no installed path yet constructs durable `not-delivered` evidence. A provider-neutral task-card model verifies a human-signed native action under operator-pinned company, agent, connection, delivery and policy facts. Only that approved card may initialize the read journal. A native verifier projects one signed agent action and exact human-issued terminal grant into a private closed release request; the journal binds its actor, human issuer, task-card commitment, listed source, recipe digest and connection generation before charging. An internal engine path now joins that task, connection, credential lease, bounded provider GET, projection, ledger and channel, rechecking the connection and expiry before release entry. A synthetic joined test uses a subject-bound connection, real native proof, an in-process loopback provider and a separately keyed Unix socket peer; it verifies one provider call, the five projected bytes, the agent acknowledgement and persisted accounting. The read operator command, multi-host store, full agent isolation and live run remain unimplemented. This is synthetic construction evidence, not an installed managed-release claim.

The read recipe needs its own qualification gate. A qualification for the installed write recipe cannot qualify a different read digest, even when both records lease the same Jules grant. The internal executor now accepts a separately installed read gate and checks it before leasing and before release; the development joined test supplies an optional read gate. The operator installation must pin and load the read gate with the read recipe before this becomes an installed claim.

### 3.2 Writes use the existing general gateway

Every production provider write uses ADR 0012's data-only, credential-isolated gateway. A write recipe fixes the target origin, typed path, request shape, credential binding, limits and any observation rule. The native agent action and, for exact mode, human confirmation bind the operation ID, resource, recipe digest and exact intended effect. Provider-specific effects, idempotency and retry safety stay in vertical reference tests and operator review. The gateway reports verified, admitted, entered, response-recorded and, where available, observed stages without inventing provider success. An ambiguous entered write is outcome_unknown and is not blindly retried.

The construction contract now derives a private exact-write intent from a native-verified agent action, the signed task card, a reviewed recipe resource field and the compiled closed request. It binds the task-card commitment, action commitment, closed request commitment, operation ID, resource handle, recipe digest, connection subject/generation and verb. A second native human action must sign that same intent for exact mode; the separately enabled bounded-upfront mode cannot borrow an exact confirmation. The Google Docs and Airtable v2 write references carry task ID and card commitment fields and declare the same provider-neutral `task_binding` over their respective document and record fields. The Airtable reference proves only closed request construction under the same compiler; it uses an operator PAT and does not prove human delegation. Ordinary installed `submit` now refuses any such recipe before a claim or lease. A task-aware engine path verifies the human-signed card once at activation, stores its full card and commitment in the private journal, then checks that activation by task ID, current operator pins, expiry and revocation while verifying each fresh agent action and exact confirmation (or the separately enabled upfront mode). It derives the same intent during submission, durably reserves a write in the common task journal before the provider attempt claim, and checks the loaded connection ID, generation and provider-account-subject commitment before credential lease. Installations serving task writes therefore set the connection's account label to the provider's stable subject. It conservatively spends that write slot if a later preparation, claim or transport step fails. Development installations now expose an operator-owned CLI path with canonical private pins, one-time task activation and task submission; production remains refused because the task journal is single-host. A broker-side development shim validates the pinned demo_co generation and Jules’s separate `drive.file` grant, checks her current UserInfo subject, and pipes a short-lived bearer into a new gateway installation with that subject as the account label. It is synthetic-tested and has not installed a live gateway credential. A synthetic installed test now signs a task card, agent action and exact human confirmation, executes the Airtable-shaped write and readback through a local provider double, observes the effect and refuses replay without a second lease. This proves the common gateway path under test keys and an operator PAT, not human-provider delegation in Airtable. The human task and exact-confirmation UI now exist as optional development screens; the agent's grounded read and draft, gateway submission and live Jules edit are still pending. This owner-side CLI and credential shim are not a live delegation claim. Request/action commitments can reveal low-entropy private content if published; they stay inside confirmation custody and are not public receipts.

The gateway's installed native trust must authorize the provider action profile and the two fixed `auths-agent-task` approval profiles. Its default request audience remains the provider service for agent actions. During task activation and exact confirmation, the gateway rebinds only the verifier's expected audience to the code-defined `mcp://auths-agent-task` audience; an agent submission cannot choose that value. The operator-owned task session refuses a trust context whose anchors lack either task profile permission, namespace or audience. Activation also checks that the subject-bound connection currently approves the installed recipe. Synthetic tests verify all three action types under the same trust configuration. The installed single-host loopback test activates a signed human task once against a subject-bound connection, refuses a later descriptor change before claim, then submits an exactly confirmed agent write through the gateway after the descriptor is restored. Installation tooling and the live producer integration still need to prove this configuration with real Jules and agent identities.

**Integration seam:** AP-SPEC-070's installed company root and employee grant authorize its Google read tool only. They cannot be silently reused to sign `approve_agent_task_v1`, `confirm_agent_write_v1` or the Docs edit action. A new [operator authority builder](../../demos/google-employee-delegation/broker/src/employee_read_demo/task_write_authority.py) now issues separate root-to-human grants for those exact task tools and the reviewed provider write tool, constructs matching multi-profile trust, and prepares a human-signed child write grant to a distinct agent. Native synthetic tests verify this same structure for Google Docs and Airtable profiles. A [private operator command](../../demos/google-employee-delegation/broker/src/employee_read_demo/task_write_operator_cli.py) packages those grants and trust from the current company root, an enrolled employee and an operator-reviewed recipe digest without accessing a provider credential. Before the live milestone, Auths must run this issuance for Jules, bind the human child grant and task/confirmation actions to her browser key and the registered agent key, install the trust context in the gateway, and verify the completed proofs under current operator state. This is Auths work; demo_co supplies neither native grants nor signing keys. The browser must show the task card and exact proposed edit before Jules signs, and the agent must sign from its own process. The current loopback test uses synthetic keys and does not fill the live seam.

The AP-071 workbench now has optional, owner-configured Jules task and exact-confirmation screens. It rechecks Google login, active employee enrollment, the registered agent, a digest-pinned producer write snapshot, the operator's private authority package and installed gateway pins. Jules sees the pinned account, working Doc, agent, expiry and one-write exact-confirmation mode before her browser key signs the child grant and task card. After a separate agent stages its signed proposal, the broker calls a SHA-pinned gateway binary to verify and compile the closed request, runs a fresh read-only Jules revision/ACL/baseline preflight, shows Jules the destination and complete request body, and obtains her second signature over the derived intent only if the preflight still matches. The broker stores both native human proofs privately and exports only public agent proof material. The optional workbench execution setting now activates the signed task in the private gateway journal and exposes a separate submission control after exact confirmation. Submission rechecks the staged agent proof and Jules’s read-only Doc preflight immediately before the gateway call; the signed Google revision remains the provider-side race guard. These paths still need a live Jules run, an agent grounded in a managed read, gateway provider entry and independent demo_co effect inspection before the delegation journey can be claimed.

The current gateway may need additional reviewed **provider-neutral** mechanisms: refresh or lease a subject-bound OAuth credential without exposing it to the application; bind one bounded value from a create response as a task-owned child resource for a later write; and, after an ambiguous response, bind an independently verified recovered resource only with fresh human confirmation. ADR 0013's response locator is limited to an observation path; it is not permission to turn a create response or search result into a second write target. Each new mechanism requires an ADR amendment, hostile corpus and independent evidence before live use. If a domain needs arbitrary callback logic, it does not fit this recipe path.

### 3.3 One task, separate authorities and receipts

Read and write grants are distinct; their counters and receipts remain distinct. The common task ledger correlates them by signed task ID and source/destination handles. A read receipt states whether delivery was entered, acknowledged or remains unknown; only an authenticated acknowledgement supports an agent-acknowledged claim. A write receipt proves the gateway's stage and any independently observed effect. A human-approved task does not itself prove provider permission, and a provider 2xx response does not prove the intended effect. Exact confirmation is the default for consequential writes; bounded upfront permission is explicit and may be disabled by company policy.

The current single-host task journal now derives both read and write scopes and budgets from one native-approved card. The task-aware gateway path atomically claims a write operation before the provider attempt claim or credential lease, refuses competing last-slot writes, persists the spent count across restart, rejects operation-ID reuse across read and write, and applies revocation to both. This remains construction evidence until one installed task completes an end-to-end write. A production multi-host store and corresponding installed evidence remain required.

The application may render provider labels and links supplied by the reviewed vertical, but common admission and UI state transitions must work without knowing Google IDs or Doc semantics. A second provider must reuse the same task and approval types, release and write custody, receipt vocabulary and denial behavior. A provider-specific adapter may live in a test-only vertical as an oracle, never as a second production credential-owning executor.

## 5. Google reference execution

### 5.1 Read and agent isolation

Reuse AP-SPEC-070's application-owned Google read broker for the closed read vertical. Its exact native action, current Jules connection, task limit and release gate govern the canonical Project A read. Extend that bounded Google read vertical for the working Doc's current content and a [Docs documents.get](https://developers.google.com/workspace/docs/api/reference/rest/v1/documents/get) revision read using Jules's account; a revision from another account or an old producer baseline cannot be used as the write precondition. Google says a Docs revision ID is only guaranteed for 24 hours and only returned to an editor, so read it near confirmation. Record bounded release receipts without logging document bodies. The agent is a distinct process/principal with only its own signing key and the approved released content. The diagnostic that keeps agent and broker in one process does not qualify.

The installed milestone may use this bounded broker while §3.1 is built, but must label its read path as Google-specific. Its current private receipt includes an unkeyed `content_sha256`; that value MUST be omitted from public AP-SPEC-071 results and exports, or replaced by a custody-held keyed commitment before they are shown. It does not satisfy §3.1's full release-receipt contract. Full provider-neutral AP-SPEC-071 acceptance requires the managed release capability and cross-provider conformance in §6.

### 5.2 Edit an existing Google Doc

ADR 0012 makes the data-only gateway the single production provider-write path. The Auths application and agent MUST NOT send a credential-bearing Google write directly. A reviewed, operator-pinned recipe issues one closed Google Docs documents.batchUpdate JSON request to the fixed working Doc ID. For the first fixture, it replaces one unique marker in one tab with bounded approved text; the response must report exactly one replacement. The exact marker, replacement bytes, operation ID, recipe digest, Doc ID and Jules-observed revision are signed in her confirmation and the agent's action. The request uses requiredRevisionId. An altered byte, stale revision, changed target or replacement count other than one cannot be recorded as the approved effect.

The [offline Google edit reference](../../demos/google-employee-delegation/write_reference/README.md) now compiles the exact `/{documentId}:batchUpdate` path and one-request JSON body. The fixed suffix is the provider-neutral [ADR 0018](../adr/0018-typed-path-field-suffix.md) mechanism, with [Case 0010](../research/domains/abstraction-cases/0010-typed-path-field-suffix.md) recording a second independent API shape. These are construction tests, not a qualified connection or live edit. The current gateway retains only the complete response's status and digest; it does not yet record the Docs `replies[0].replaceAllText.occurrencesChanged` value. A reviewed, bounded response assertion or equivalent independent response evidence must establish exactly one before the milestone can claim the approved effect. The separate producer readback remains mandatory.

### 5.3 Create and populate a new Google Doc

[Google Drive files.create](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/create) can create a blank Google Doc in a specified parent with JSON metadata; Google's [Docs creation guide](https://developers.google.com/workspace/docs/api/how-tos/documents) documents this folder path. Google Docs documents.batchUpdate can then insert the approved content using JSON. Both must go through separately reviewed gateway recipes and the same Jules-scoped connection. The create action fixes the Project A parent ID, MIME type, title, permitted visibility and operation budget. It also writes one fresh, opaque, run-owned recovery marker in Drive custom `properties`, bound privately to the task and operation ID. The marker is metadata for locating a possible result, not a provider idempotency key or proof that the create happened. A complete create response's new file ID is verified and bound to that task and receipt. The populate action may use **only that response-derived child ID or a separately verified recovered-child binding**, never an arbitrary agent ID. A typed, bounded child-resource binding needs reference semantics, hostile cases, recipe digest review and ADR 0013 evidence before implementation.

demo_co's existing `appProperties` ownership markers stay producer-owned. The recovery marker uses cross-client-visible `properties` so independent verification does not depend on Auths and demo_co sharing an OAuth client. Because a party with sufficient file edit rights may change a custom property, the marker only nominates a candidate; it never replaces parent, account, timing, child-count and independent producer checks.

One exact human confirmation covers the proposed title, parent and complete initial content, and both intended effects. Creation and population are not atomic together. If the create response is lost, Auths has **no returned ID**. Google's [Drive search](https://developers.google.com/workspace/drive/api/guides/search-files) can query a custom property, so a separately reviewed, bounded recovery read searches the pinned parent and drive for the exact marker with Jules's connection. It follows every page within a fixed page/result cap, rejects `incompleteSearch` or an exceeded cap, and verifies each candidate's ID, parent, MIME type, title, marker and observed account/shared-drive context against the task. demo_co independently checks any candidate through its producer probe. Exactly one consistent candidate may be proposed as a recovered-child binding; Jules must sign a fresh confirmation binding that ID and the independent evidence to the original approved title, parent and content before population. Zero candidates, multiple candidates, an incomplete search or a failed independent check leave `outcome_unknown`: no populate, no automatic create retry, and no claim that the file does not exist. [Drive pre-generated IDs do not support ordinary Google Workspace Docs](https://developers.google.com/workspace/drive/api/guides/create-file), so they are not a fallback here. Any future retry rule would need provider evidence proving non-effect or a documented idempotency guarantee, reviewed in the Google vertical and admitted through the gateway; an empty search alone is insufficient.

If creation is known to have succeeded but population is unknown or fails, show an incomplete artifact and reconcile the known ID before any new action. Do not create another file to hide an ambiguous first result. The producer checks the actual parent, title, content, owner/permissions, count of run-owned children and unchanged excluded state. Cleanup is explicit and occurs only after evidence capture.

## 7. Exact confirmation and operating rules

The write proposal screen shows the source citation and content destination; before and after text; connected human account, destination label/link and opaque resource handle; applicable version/precondition; agent identity; recipe; maximum effect count; expiry; and whether this is edit or create. The human's confirmation signs a canonical digest covering those fields and the exact content bytes or their canonical digest. The agent's later action must match byte-for-byte. For Google, the screen also resolves the Doc/folder IDs and current revision through its reviewed vertical. Google login alone is not a write confirmation.

Revocation blocks new admission and leases after its documented commit point. It cannot retract released read content or undo an entered write. Read release and write effect have distinct receipts and limits. Agent and gateway have separate filesystem and network boundaries; the agent cannot inspect the OAuth vault, human signing key, operator interface or admin fixture grant. A prompt inside the source document is untrusted data and cannot change the approved destination. Logs, export and evidence contain no tokens or private document text.
