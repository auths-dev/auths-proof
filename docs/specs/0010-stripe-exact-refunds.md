# 0010: Auths for exact Stripe refunds

Status: Implemented
Target: MVP plus public end-to-end demonstration  
Profile: `auths.stripe.exact-refund/1`  
Product package: `product/integrations/auths-stripe`  
Demo: `demos/stripe-refund`

## 1. Decision

Build one vertical Stripe product package that lets an untrusted agent propose one exact refund without receiving a Stripe API key.

The first profile is test-mode-only. It authorizes a single refund for one exact Stripe account, Charge or PaymentIntent, amount, currency, reason, API version, and metadata commitment. The protected executor claims the action, obtains the protected restricted key, submits the exact request with a deterministic idempotency key, reconciles ambiguous responses, and records later Stripe observations separately.

This is not a generic Stripe proxy and not a payment-operations chatbot.

## 2. Product claim

An API key or OAuth scope can permit creation of refunds. Auths binds that capability to one exact financial action:

> refund exactly 1000 USD minor units from this test-mode charge, for this reason, on this Stripe account and API version, once, before expiry.

Changing 1000 to 1001, changing the charge, switching account context, adding transfer reversal, or replaying the request is not authorized.

## 3. Goals

The MVP must:

1. model a Stripe refund as a canonical exact action;
2. acquire fresh payment evidence before authorization;
3. bind account, livemode, object identities, amount, currency, parameters, API version, and configuration;
4. deny live-mode operation structurally, not by UI convention;
5. claim before acquiring the Stripe key;
6. use both Auths replay claims and Stripe idempotency correctly;
7. distinguish API acceptance, refund state, and webhook observation;
8. reconcile timeouts without blind duplicate requests;
9. produce redacted portable receipts; and
10. provide a real Stripe test-mode demonstration.

## 4. Non-goals

The MVP does not:

- operate in live mode;
- create payments;
- issue credits outside Stripe refunds;
- create payouts or transfers;
- reverse transfers or refund application fees;
- update customers or payment methods;
- accept arbitrary metadata;
- manage disputes;
- expose a general Stripe API credential;
- claim that an accepted refund has settled at the banking network; or
- use Stripe idempotency as the only replay defense.

## 5. Trust and credential model

### Untrusted

- agent-provided object descriptions;
- browser fields;
- formatted currency strings;
- webhook requests before signature and event validation;
- user-facing payment labels;
- arbitrary metadata; and
- network errors interpreted without reconciliation.

### Trusted for the MVP

- Auths core;
- the Stripe vertical package;
- protected executor;
- configured Stripe test account;
- restricted test-mode key;
- webhook signing secret;
- claim and receipt stores;
- pinned Stripe API version; and
- required verifier configuration.

The frontend and agent-facing processes must not contain the API key or webhook secret. The executor retrieves the restricted key only after a successful claim.

## 7. Canonical action

```text
StripeExactRefundV1 {
  profile
  executor_audience
  stripe_account_id
  stripe_api_version
  livemode
  charge_id
  payment_intent_id
  amount_minor
  currency
  reason
  metadata
  refund_application_fee
  reverse_transfer
  expected_charge_amount
  expected_amount_refunded
  expected_refundable_amount
  charge_evidence_digest
  idempotency_key
  required_configuration
  observed_at
  expires_at
  nonce
}
```

Normative requirements:

- `profile` equals `auths.stripe.exact-refund/1`;
- `livemode` is false;
- the configured test account ID matches;
- `amount_minor` is a positive integer and never a decimal string;
- `currency` is the lower-case currency reported by Stripe;
- both object identity and their relationship are committed when available;
- `refund_application_fee` and `reverse_transfer` are false;
- `reason` is either absent or an allowed Stripe enum;
- metadata is generated by the package from fixed keys;
- `idempotency_key` is deterministically derived from the profile and action digest; and
- every form-encoded outbound parameter is derived from the verified action.

The action’s digest calculation uses a representation without the derived `idempotency_key`, then the key is derived with a domain-separated hash. This avoids a circular commitment.

## 8. Money representation

Money is always represented as:

```text
MoneyV1 {
  currency
  amount_minor
}
```

The package owns currency validation and display exponent rules. Authorization compares integer minor units, never localized text or floating point.

The UI may render `$10.00`, but the proof and request authorize `currency = "usd"` and `amount_minor = 1000`.

## 9. Fresh Stripe evidence

The protected read path retrieves the relevant PaymentIntent and Charge using the configured account context and API version.

Evidence includes:

- Stripe account identity;
- API version;
- object IDs and relationship;
- `livemode`;
- charge status, paid state, captured state, currency, amount, amount refunded, and refunded flag;
- calculated refundable amount;
- dispute and refund state relevant to policy;
- Connect context if present;
- observation time;
- normalized response commitment; and
- evidence-source configuration.

Authorization denies when:

- `livemode` is true;
- account or API version differs;
- charge is not paid or captured as required;
- currency differs;
- requested amount exceeds the fresh refundable amount;
- the object is fully refunded;
- a disallowed dispute or Connect condition exists;
- evidence is stale; or
- the response contains a state the pinned profile does not understand.

## 10. Required and executed configuration

```text
StripeVerifierConfigurationV1 {
  profile
  canonicalization_version
  allowed_test_account_ids
  allowed_api_versions
  allowed_currencies
  maximum_refund_minor_by_currency
  allowed_reasons
  maximum_evidence_age_seconds
  maximum_authorization_lifetime_seconds
  allow_partial_refunds
  allow_refund_application_fee
  allow_reverse_transfer
  allowed_metadata_keys
  receipt_schema_version
}
```

The verifier emits both `required_configuration` and `executed_configuration`. Canonical inequality yields `verifier-configuration-mismatch` before claim or key acquisition.

A mandatory unit test changes only the USD maximum by one minor unit and proves the mismatch is denied while both configurations remain visible.

## 11. Authorization pipeline

The verifier:

1. applies hard input limits;
2. decodes and canonicalizes the action;
3. verifies proof chain, audience, expiry, and nonce;
4. compares required and executed configuration;
5. verifies test account and `livemode=false`;
6. checks evidence source and freshness;
7. verifies Charge and PaymentIntent identity;
8. recomputes refundable amount;
9. checks exact amount, currency, reason, and metadata;
10. denies Connect side effects;
11. recomputes the deterministic idempotency key; and
12. emits a decision without accessing the Stripe key.

Human-readable prices and descriptions are never authorization inputs.

## 12. Claim and execution order

```text
verify
  -> claim action digest
  -> acquire restricted Stripe test key
  -> re-read cheap critical preconditions
  -> POST exact refund with deterministic idempotency key
  -> persist API receipt
  -> retrieve refund
  -> process signed webhook observations
```

The executor sends an explicit Stripe account context when required and pins the committed API version. It uses a typed request builder with an allowlist of fields. It cannot forward an agent-provided request body or headers.

## 13. Idempotency and replay

Stripe idempotency and Auths claims solve different problems:

- Auths claims prevent a valid authority from being deliberately or concurrently reused across the product boundary.
- Stripe’s idempotency key helps reconcile duplicate delivery of one provider request.

The Auths claim is durable beyond any provider retention window. The deterministic Stripe key is unique to the action digest and never reused for different parameters.

An idempotency parameter mismatch is a hard execution failure and security signal.

## 14. Outcomes

The product separately represents:

1. `authorized`;
2. `provider_request_accepted`;
3. `refund_created`;
4. `refund_status_observed`; and
5. `webhook_confirmed`.

The Stripe refund object may have a status that changes after creation. A successful HTTP response does not mean funds have completed movement through external banking networks.

The Auths authorization receipt is immutable. Later observation receipts append state; they do not rewrite the authorization decision.

## 15. Ambiguous outcomes and reconciliation

For a timeout after request submission:

1. preserve the action claim as `outcome_unknown`;
2. retry only through the same protected request path with the identical idempotency key and parameters, within a bounded reconciliation policy;
3. retrieve the resulting refund by stored provider ID when available;
4. list or correlate refunds using fixed Auths metadata when necessary;
5. compare charge, amount, currency, account, and metadata with the action;
6. record `reconciled_created`, `reconciled_not_created`, or `indeterminate`; and
7. never create a new action or idempotency key silently.

Reconciliation does not authorize a different remaining refundable balance.

## 16. Webhooks

The webhook endpoint:

- verifies Stripe’s signature against the raw request body;
- applies a timestamp tolerance;
- rejects unsupported events and API versions;
- deduplicates event IDs;
- verifies account and object relationships;
- retrieves authoritative state when required;
- appends an observation receipt; and
- never treats webhook contents as a new authorization.

Webhook signing secrets and raw payloads are not included in public receipts.

## 17. Receipts

### Decision receipt

Action digest, proof identity, test account commitment, object commitments, money, evidence digest and age, required/executed configuration, verdict, stable code, and stage.

### Claim receipt

Action digest, claim ID, claimant audience, transition, and replay outcome.

### Stripe API receipt

Request digest, idempotency-key commitment, API version, account commitment, HTTP classification, Stripe request ID, refund ID commitment, amount, currency, initial status, and timestamps.

### Observation receipt

Refund ID commitment, status, charge relationship, webhook event ID commitment or retrieval source, observation time, and previous receipt digest.

Public receipts use synthetic test IDs or commitments. Credentials and webhook secrets never appear.

## 19. End-to-end demo

### Scenario

The protected demo environment seeds a real Stripe test-mode payment. The synthetic agent proposes refunding a visible amount, for example USD 10.00.

The visitor sees:

- test-mode account and payment facts;
- original amount, already-refunded amount, and remaining refundable amount;
- exact proposed refund in display and minor units;
- authorization verdict and configuration parity;
- claim and Stripe request state;
- resulting refund status; and
- linked receipts.

The primary successful path creates a real Stripe test-mode refund. A fixture-only simulation is not sufficient.

### Experiments

- exact refund;
- amount increased by one minor unit;
- different Charge;
- different currency;
- stale refundable balance;
- transfer reversal enabled;
- live-mode bit changed;
- verifier configuration changed; and
- replay the executed action.

Because refunds consume the seeded payment balance, the demo provisions a fresh test payment per isolated session or scenario. Reset must create new test objects; it must never falsify or delete prior receipts.

### Layout and copy

Controls and live results are side by side on desktop and directly adjacent on mobile. The amount mutation and resulting denial must be visible together.

Copy explains the concrete events:

- the agent proposed a refund;
- it has no Stripe API key;
- Auths authorized or denied these exact parameters;
- the protected executor did or did not call Stripe; and
- Stripe reports this refund state.

Avoid abstract slogans.

### Frontend delivery contract

The frontend is a required part of the implementation, not optional follow-up work. A backend-only implementation, API explorer, static mockup, or page that never reaches the native refund executor does not satisfy this specification.

Follow the established GitHub and Radicle demo interaction model:

- one primary workbench places selectable experiments beside the current verdict and refund result;
- selecting an experiment immediately updates the exact proposed refund and predicted decision;
- executing it calls the deployed native backend and renders its returned stable code, required/executed configuration commitments, claim state, Stripe effect, and receipt links;
- loading, unavailable, denied, indeterminate, authorized, executed, observed, and replay states are visibly distinct;
- the successful path creates the real Stripe test-mode refund, while every denied path proves that Stripe was not called; and
- desktop and mobile layouts keep the control that caused a result adjacent to that result.

### Receipt interface contract

Receipts must be understandable without navigating away from the experiment
that produced them:

- after every attempted execution, the primary workbench exposes the complete,
  pretty-printed machine-readable receipt inline beneath the live result;
- the inline JSON is loaded from the real receipt API and is not reconstructed
  from frontend state;
- the workbench’s receipt link opens a dedicated
  `/receipts/{session-or-workflow-id}` page, not the raw JSON API response;
- the dedicated page summarizes the decision, stable code, action and evidence
  commitments, required/executed configuration relationship, credential or
  provider boundary, and observed effect before offering the complete raw JSON;
- missing, expired, malformed, or unverifiable receipt identifiers render an
  explicit fail-closed receipt page; and
- browser tests cover both the inline viewer and the dedicated receipt route.

Browser-level end-to-end tests must start from the rendered page and exercise readiness, fresh session creation, exact refund, at least one material denial, replay, Stripe result rendering, and receipt inspection through the same public API routes used in production. Static DOM assertions and backend-only integration tests are necessary but insufficient.

Completion requires a publicly reachable frontend URL and a publicly reachable native API deployment. Opening `index.html` through `file://`, serving only on localhost, committing Vercel/Fly configuration without deploying it, or deploying a frontend whose API is unavailable does not satisfy this specification. Before handoff, test the public Vercel URL against the public Fly deployment and record the tested URLs and release identifiers.

### Design and deployment

Use the `auths-proof-site` visual system. Deploy the frontend on Vercel and the native executor/webhook service on Fly.io. Use Stripe test mode exclusively, durable claims and receipts, per-session seeded objects, signed webhooks, explicit CORS, and documented health/readiness endpoints.

Deployment validation must inspect frontend assets, environment variables, source maps, logs, and error responses for Stripe keys and webhook secrets. The public page prominently and accurately labels test mode.

## 20. API surface

```text
POST /api/v1/sessions
GET  /api/v1/sessions/{id}
POST /api/v1/authorize
POST /api/v1/execute
GET  /api/v1/executions/{id}
GET  /api/v1/receipts/{id}
POST /api/v1/webhooks/stripe
GET  /healthz
GET  /readyz
```

The execute endpoint accepts a signed Auths envelope and session handle. It does not accept a Stripe key, arbitrary Stripe URL, account header, raw form body, or free-form metadata.

## 21. Testing

### Unit and conformance

- money and currency canonicalization;
- action and evidence vectors;
- required/executed configuration mismatch;
- changed amount, currency, object, account, version, and livemode;
- deterministic idempotency derivation;
- request-field allowlist;
- evidence expiry;
- webhook raw-body signature fixtures;
- browser/native parity;
- concurrent claim and replay.

### Stripe test-mode integration

- seed payment and exact full refund;
- partial refund;
- amount exceeds remaining balance;
- duplicate request with same idempotency key;
- same key with altered parameters;
- timeout and reconciliation;
- webhook duplication and reordering;
- unsupported event;
- changed API version;
- restricted key lacks unrelated permissions.

### Security and deployment

- denial never reads the API key;
- frontend bundle and source maps contain no secret;
- logs, traces, receipts, and errors are scrubbed;
- service cannot operate on a non-allowlisted account;
- live-mode objects are always denied;
- Vercel/Fly connectivity, CORS, health, readiness, and webhook routing work; and
- session reset produces fresh test objects without receipt reuse.

### CI

Enforce package boundaries, deterministic offline fixtures, pinned API schema/version assumptions, separation of live contract tests, WASM/native dependency separation, secret scanning, and workspace Rust policies.

## 22. Acceptance criteria

1. The agent proposes an exact refund without a Stripe key.
2. The successful demo creates a real Stripe test-mode refund.
3. The action binds account, object, amount, currency, API version, evidence, and configuration.
4. A one-minor-unit change denies.
5. Live mode and Connect side effects are structurally denied.
6. Claim precedes key acquisition.
7. Replays cannot create a second refund.
8. Ambiguous requests reconcile with the same provider idempotency key.
9. API acceptance and later refund observations remain separate.
10. Required and executed configuration are visible and equal on success.
11. Browser and native decisions match.
12. Core crates remain independent of Stripe.
13. The deployed frontend completes exact, denial, replay, Stripe-observation, and receipt flows against the deployed native backend.
14. Browser-level end-to-end tests fail if frontend/backend wiring, CORS, readiness, interaction, or result rendering breaks.
