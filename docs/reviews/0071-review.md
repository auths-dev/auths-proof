1. **[P1] Close the unsigned observation route for task-bound recipes.**

   **Location:** [product/runtime/auths-gateway/src/engine.rs:1605](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/product/runtime/auths-gateway/src/engine.rs:1605) (read-back branch, lines 1605–1634); [product/runtime/auths-gateway/src/recipe.rs:963](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/product/runtime/auths-gateway/src/recipe.rs:963); [product/runtime/auths-gateway/src/app.rs:255](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/product/runtime/auths-gateway/src/app.rs:255).

   Ordinary `submit` rejects task-bound recipes, but `observe(ReadBack)` does not. The application frame requires no proof, task ID, recipient or release allowance. With the new Airtable task-write recipe, a static PAT and a provisioned observer, an application client can supply `{"record_id":"<task-excluded-record>"}`. The gateway constructs the GET, leases the credential, and returns the actual `DemoStatus` as the signed observation's `value`. Repeating it, including after task revocation, bypasses the managed read scope, byte/call budgets and authenticated delivery channel. The materializer path's refusal to provide an ordinary lease does not protect supported static-secret installations.

   Reject ordinary observations for task-bound recipes, or route any content-bearing result through native task admission and managed release; also authorize stored outcome/pre-entry observations by task before exposing them. Add an application-socket regression using a provisioned observer, an excluded Airtable record and a revoked task, asserting zero provider calls and no returned value. This violates §3.1's explicit prohibition on using existing gateway GETs as an agent-facing release API.

2. **[P1] Establish an OS-enforced boundary for the managed agent before treating credential isolation as demonstrated.**

   **Location:** [product/runtime/auths-gateway/src/release_channel.rs:192](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/product/runtime/auths-gateway/src/release_channel.rs:192) (lines 192–200); [demos/google-employee-delegation/agent/src/employee_read_agent/release_channel.py:24](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/demos/google-employee-delegation/agent/src/employee_read_agent/release_channel.py:24); [docs/program-log/2026-10-25-ap071-airtable-live.md:49](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/docs/program-log/2026-10-25-ap071-airtable-live.md:49).

   The gateway requires the socket and its private directory to belong to its own UID; the receiving agent independently requires that directory to belong to the agent's UID. The documented local process-only run consequently shares an OS identity, and the Airtable evidence explicitly acknowledges this. In that deployment, a compromised agent can open the gateway's owner-readable credential/source files and task journal, or invoke the owner CLI, despite having only a narrow signed task. A separate signing key and a 0700 directory do not restrict another process under the same UID. This defeats grant enforcement by allowing direct use of the provider credential.

   Supply a managed-channel deployment with separate users or enforced mount/process/network isolation, and test from the actual agent that credential files, operator state/interfaces and direct provider egress are inaccessible. The existing AP-070 Compose configuration runs the broker-read journey and does not wire the AP-071 gateway/socket path. §7 and §8.3 therefore lack convincing isolation evidence; do not substitute the older container probe for this execution path.

3. **[P2] Recheck task revocation and expiry before read credential lease and provider entry.**

   **Location:** [product/runtime/auths-gateway/src/release_execute.rs:397](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/product/runtime/auths-gateway/src/release_execute.rs:397) (lines 397–410 and 441–449).

   After the durable read reservation, `fetch_projected` checks only connection identity and qualification, then leases/materializes a credential and sends the GET. It never reloads the task at either boundary. For example, pause an admitted read during OAuth refresh, commit `task-revoke`, then resume: the connection is unchanged, so the provider GET still executes. With a static credential, a pause across task expiry likewise leaves a valid 30-second lease able to enter the provider. The later `enter_release` check prevents agent delivery, but does not prevent this post-revocation/provider access or a new lease acquired after revocation.

   Apply the current-task check used by the write path before leasing and immediately before the read transport, preserving the spent reservation and recording refusal. Add barrier-controlled tests for revocation during materialization and expiry with a static lease, with zero subsequent provider requests. §7 and ADR 0020 require these authority checks; the existing revoke-then-submit tests do not exercise this interleaving.

4. **[P2] Reconcile a recorded create using its original verification time.**

   **Location:** [product/runtime/auths-gateway/src/engine.rs:2465](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/product/runtime/auths-gateway/src/engine.rs:2465) (lines 2465–2494); [demos/google-employee-delegation/agent/src/employee_read_agent/write.py:93](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/demos/google-employee-delegation/agent/src/employee_read_agent/write.py:93).

   The agent's action lasts at most 300 seconds, but `reconcile_created_child` verifies that original action at the recovery wall-clock time. If the gateway records a successful create response and crashes before persisting the child binding, a restart six minutes later rejects the original proof even though the 30-minute task and effect plan remain active. A newly signed action cannot replace it because the stored attempt/plan binds the original action commitment. The response-less recovery route explicitly refuses a recorded response, so it cannot recover this case either; the existing child is stranded and the original population cannot proceed.

   Authenticate the original create against the durable attempt's evaluation time, while checking current task/connection/recovery authority separately, as the response-less recovery path already does. Cover both recorded-plan and exact-confirmation reconciliation after the original action expires, asserting one create, one child binding and no create replay. The immediate synthetic restart case is insufficient evidence for §5.3's recovery contract.

5. **[P2] Move Google credential implementation out of the shared gateway executable.**

   **Location:** [product/runtime/auths-gateway/src/bin/auths-gateway.rs:14](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/product/runtime/auths-gateway/src/bin/auths-gateway.rs:14) and [product/runtime/auths-gateway/src/bin/auths-gateway.rs:3427](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/product/runtime/auths-gateway/src/bin/auths-gateway.rs:3427); [product/runtime/auths-gateway/src/bin/google_custody.rs:249](/Users/bordumb/workspace/repositories/auths-proof-base/auths-proof-ap070/product/runtime/auths-gateway/src/bin/google_custody.rs:249).

   The common executable unconditionally compiles `google_custody` on Unix, parses Google-specific pins, and constructs `GoogleCustodyMaterializer` directly. That module knows Google's token/UserInfo endpoints, exact OAuth scopes, Jules-specific source naming and the demo_co Google write-verification schema and probe flags. Consequently, installing a second renewing provider requires changing the shared executable; an unrelated change to the demo_co Google export can prevent the common task engine from loading its configured adapters. These are executable provider/demo semantics, not operator-reviewed recipe data.

   Keep the shared engine's closed materialization contract, but put Google grant parsing, OAuth and producer validation in a separately owned custody integration/development composition boundary. Demonstrate another credential source through the same installed interface without modifying the common binary. The development-only command check limits deployment exposure; it does not satisfy §2/§3's provider-neutral ownership requirement.
